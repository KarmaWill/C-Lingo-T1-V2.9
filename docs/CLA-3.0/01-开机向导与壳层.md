## 一、概述与本篇范围

### 1.1 本篇为什么重要

C-LingoAIOS 不是一个装在平板上的 App，而是**开机即接管整台设备的学习操作系统外壳**。这决定了本篇覆盖的两块内容都是「用户第一眼看到的东西」：

- **开机向导**是产品的第一屏，也是唯一一次能强制用户按顺序做完五件事的机会。它的完成率直接决定 `00` 第三节的头号 KPI。
- **壳层**是其余 66 条路由共用的容器。壳层的一个尺寸错误会同时出现在 66 个页面上，而一个页面的错误只影响它自己。

因此本篇的缺陷优先级普遍高于分域文档——**同样的一处代码问题，在壳层里的影响面是在业务页里的 66 倍。**

## 二、开机向导 · 全流程状态机

### 2.1 现状基线

向导不是一条路由，而是 `/Home` 与 `/library` 上的**全屏覆盖层**。Provider 链（`App.tsx:141-216, 223-228`）：

```text
LocaleProvider → ThemedApp → ThemeProvider → OnboardingProvider
  → MainLayout → FeedbackProvider → 页面 Routes
```

`OnboardingContext.tsx:31,55` 计算：

```ts
active = (pathname === '/Home' || pathname === '/library') && !onboarded
```

`HomeEntryPage.tsx:5-8` 据此把整页替换为 `OnboardingFlow`。内部 5 步用 `STEPS`（`OnboardingFlow.tsx:107-113`）定义，step 索引 0–4。

### 2.2 3.0 需求 · 步骤定义

| step | id | 进度轨标签 | 页面标题 | 副标题 |
|---:|---|---|---|---|
| 0 | `language` | Language | Please Select Your Language | 无 |
| 1 | `wifi` | WiFi Connection | Select WiFi | Please select an available Wi-Fi network |
| 2 | `email` | Activation | Activate Your Device | 无 |
| 3 | `profile` | Personal Info | Complete Your Profile | Help us understand you better and personalize your learning plan. |
| 4 | `path` | Complete | Choose Your Learning Path | Select the best-fit option. You can adjust it later in Settings. |

**步骤顺序不可调整、不可跳步、不可乱序进入。** 顺序依据：语言必须最先定（否则后面四步的文案用户看不懂）；WiFi 必须在激活之前（激活需要网络）；个人资料在激活之后（激活失败就不必采集个人数据）；学习路径最后（它的 CTA 直接导航离开向导）。

### 2.3 3.0 需求 · 推进与回退控制

`canNext` 决定 Next 按钮是否可点；`showNext` 决定 Next 按钮**是否渲染**。两者是不同的机制，测试要分开验。

| step | `canNext` 条件 | `showNext` 条件 | Next 按钮文案 |
|---:|---|---|---|
| 0 | 恒 `true`（有默认选中项） | 恒 `true` | Next |
| 1 | `wifiId !== null` | **`wifiOn === true`** | Next |
| 2 | `emailOk && tos` | 恒 `true` | Activate & Proceed |
| 3 | `nickname` 与 `dob` 均非空 | 恒 `true` | Confirm（无 chevron） |
| 4 | 恒 `true`（默认选中 `clingo`）；`hskOpen` 时置 `disabled` | 恒 `true` | 随选中卡的 CTA 变化 |

**Step 1 的 `showNext` 是全流程唯一会让按钮整颗消失的分支**，需求要保留这个行为：WLAN 开关关闭时不该出现一个永远点不动的 Next，那比没有按钮更让人困惑。但**必须补一句引导文案**说明「打开 WLAN 以继续」，否则用户看到的是一个没有出路的页面。

**Go Back**（`step > 0` 时渲染在进度轨底部，`margin-top: auto`）：关闭 HSK 弹窗并 `step - 1`。

> **3.0 需求**：Go Back **不清除各步表单 state**，用户回退再前进时已填内容必须还在。这一点当前代码已正确实现，需求在此固化，防止后续重构时丢掉。

### 2.4 3.0 需求 · 流程图

```text
              ┌─────────────────────────────────────────────┐
设备首次开机 → │ Step 0 语言（10 张卡，默认 en 或当前 locale）│
              └───────────────────┬─────────────────────────┘
                                  ↓ Next（恒可点）
              ┌─────────────────────────────────────────────┐
              │ Step 1 WiFi                                 │
              │   WLAN 关 → Next 不渲染                     │
              │   WLAN 开 → 列表出现 → 选网络后 Next 可点   │
              └───────────────────┬─────────────────────────┘

              └───────────────────┬─────────────────────────┘

              ┌─────────────────────────────────────────────┐
              │ Step 3 个人资料（头像/昵称/生日/性别）       │
              └───────────────────┬─────────────────────────┘
                                  ↓ Confirm
              ┌─────────────────────────────────────────────┐
              │ Step 4 学习路径（三张卡）                    │
```

### 2.5 异常态

| 场景 | 3.0 要求 |
|---|---|
| 向导进行中刷新页面 | 回到 step 0。**已填内容允许丢失**（向导总时长目标 ≤ 150 秒，不值得为此做草稿持久化），但不得白屏或卡在中间步骤 |
| `localStorage` 不可用（隐私模式 / 配额满） | 向导仍可走完，`finish` 时写入失败要提示「无法保存设置，请检查存储空间」，**不得静默失败让用户下次重走一遍** |
| 向导进行中断网 | Step 0/3/4 不受影响；Step 1/2 见各章异常态 |

### GWT · 全流程

- **Given** 一台从未使用过的设备（`clingo-onboarded-v1` 不存在），**When** 用户打开应用落地 `/Home`，**Then** 页面被向导覆盖层整页替换，进度轨显示 `1/5`，当前步骤为 Language。
- **Given** 用户处于 step 3 且已填昵称「Alex」，**When** 点击 Go Back 回到 step 2、再点 Next 回到 step 3，**Then** 昵称输入框内仍为「Alex」。
- **Given** 用户处于 step 1 且 WLAN 开关为关闭状态，**When** 观察页面右下角，**Then** Next 按钮不存在于 DOM 中，且页面展示引导文案提示打开 WLAN。
- **Given** 用户处于 step 4 且 HSK 等级弹窗已打开，**When** 尝试点击弹窗背后的 Next 按钮，**Then** Next 处于 `disabled` 状态且点击无任何反应。
- **Given** 浏览器 `localStorage` 已被禁用，**When** 用户在 step 4 点击「Start C-Lingo Level 1」，**Then** 展示「无法保存设置」提示，且不导航到 `/Home`。

## 三、Step 0 · 语言选择

### 3.1 现状基线

10 张语言卡按 2×5 网格排列（`OnboardingFlow.tsx:116-127, 393-410`），每张卡含母语名与国旗 emoji。列表：`zh` / `en` / `vi` / `id` / `ja` / `ko` / `th` / `es` / `fr` / `ar`。

默认选中项 = 当前 `locale.id` 在表中的匹配项，无匹配则 `en`。`canNext` 恒 `true`。

**其中 `id`（印尼语）与 `th`（泰语）的 `localeId` 为 `null`**——选中后界面语言不发生任何变化，仍是英文，且无任何提示。这是 D7 的一半。

### 3.2 3.0 需求 · 字段与取值

| 字段 | 类型 | 取值 | 默认 | 校验 |
|---|---|---|---|---|
| 选中语言 | 单选 | 语言表中的 `id` | 当前 `locale.id`，无匹配则 `en` | 必选，但因有默认值故不会为空 |

控件规格：

| 项 | 要求 |
|---|---|
| 布局 | 2 行 × 5 列网格，不滚动（首页一屏原则同样适用于向导） |
| 卡片内容 | 母语名（不是英文名）+ 国旗 emoji。母语名让用户不必先懂英文就能找到自己的语言 |
| 选中态 | `border-color: #00b4a0`，`background: #f3faf6` |
| 最小可点区域 | 按食指指腹，见 `06` 第十一章给定数值 `[待确认]` |
| `role` | `radiogroup` / `radio`，`aria-checked` 正确反映选中态 |

### 3.3 3.0 需求 · 语言表必须单一数据源（D7 的一半）

**这是 Step 0 的核心需求，不是优化项。** 详见第十二章，此处只给出对本步骤的约束：

1. 向导语言卡列表**必须**与全局 `APP_LOCALES` 同源，不允许存在第二份硬编码列表。
2. 任何出现在语言卡里的语言，**必须**有可用的 `localeId` 与译文资源。
3. 若某语言已列入产品规划但译文未就绪，有两种合法处理，**不允许第三种（当前的做法）**：
   - 从向导语言卡中移除，不展示；
   - 展示为**明确标注的占位态**（如「即将支持 · 界面暂用英文」），点击后仍可继续，但用户事前知情。

当前行为——展示为可正常选择的卡片、选中后静默地不生效——是**欺骗性交互**，必须消除。

### 3.4 异常态

| 场景 | 3.0 要求 |
|---|---|
| 语言资源加载失败 | 回落 `en` 并在页面顶部提示，不白屏 |
| 选中语言的字体未加载完成 | 先用系统字体渲染，字体到位后替换。不得因等字体而空白（见 `06` 性能预算） |
| 用户选择 `ar` | 立即生效：文案切阿语、字体切 `Noto Sans Arabic`、**`documentElement.dir` 置 `rtl` 并整页镜像**（见第十二章） |

### GWT · Step 0

- **Given** 设备为全新状态且系统语言未知，**When** 进入 step 0，**Then** 默认选中「English」卡，Next 按钮可点。
- **Given** 用户在 step 0，**When** 点击「العربية」卡，**Then** 页面文案立即切换为阿拉伯语、字体切换为 `Noto Sans Arabic`、`document.documentElement.dir` 值为 `rtl`，且进度轨从页面右侧显示。
- **Given** 3.0 语言表中某语言的译文资源未就绪，**When** 用户查看 step 0 的语言卡，**Then** 该卡要么不出现，要么带有「界面暂用英文」的明确标注；**不存在**「看起来正常但选了不生效」的卡片。
- **Given** 语言卡共 10 张，**When** 在 960×540 最小支持分辨率下渲染 step 0，**Then** 10 张卡全部在一屏内可见，页面不出现垂直滚动条。
- **Given** 用户用食指点击语言卡的边缘区域，**When** 触点落在卡片可视边界内，**Then** 选中状态正确切换（触控目标不小于可视区域）。

## 四、Step 1 · WiFi 连接

### 4.1 现状基线

**这一步整体是 UI 模拟，不触碰系统网络。** 代码注释明确写了「一期 webview 扫不了真 WLAN」。

| 元素 | 现状 |
|---|---|
| WLAN 开关 | `role="switch"`，默认 `false`（`OnboardingFlow.tsx:265, 432-444`）。关闭时 `setWifiId(null)` |
| 刷新按钮 | 假延迟 700ms 旋转动画（L418-430），不实际扫描 |
| 网络列表 | 仅 `wifiOn` 为真时渲染。数据是硬编码 4 条 `WIFI_NETWORKS`（L152-157） |
| Next | `showNext` 依赖 `wifiOn`；`canNext` 依赖 `wifiId !== null` |

硬编码网络列表：

| SSID | 信号格数 | 加密 |
|---|---:|---|
| `C-Lingo_Office` | 3 | 是 |
| `C-Lingo_Office_5G` | 3 | 是 |
| `C-Lingo_Guest` | 2 | 是 |
| `Campus_WiFi` | 1 | 否 |

选中任一条即视为「连接成功」，**不校验密码、不实际联网**。

### 4.2 3.0 需求 · 模拟 vs 真实能力的取舍

这一步必须做真的。理由不是「假的不好」，而是**Step 2 激活需要网络**——如果 WiFi 是假的，Step 2 的激活也只能是假的，那么整条激活链路（含设备 SN 上报、TOS 同意记录）在 3.0 就都无法落地。

因此本步骤依赖**安卓原生桥**（`07` 附录 Q20，归属方取决于 Q34 / Q74 的定位裁决）。

#### 4.2.1 安卓现实：三方应用身份下做不到「应用内连 WiFi」

> **以下内容按 `07` 第七节评审纠正 3 修订。** 本节初稿列了「开启 / 关闭 WLAN」「连接指定网络（含密码）」等桥能力，安卓原生评审指出这些在三方应用身份下**不可实现**：

| 初稿设想的能力 | 安卓现实 |
|---|---|
| `setWifiEnabled` 开关 WLAN | **Android 10+ 起对三方应用无效** |
| `addNetwork` 添加网络 | **API 已移除** |
| `WifiNetworkSuggestion` / `WifiNetworkSpecifier` | 存在，但**给不了「把这个 SSID 设为默认网络」**的语义 |
| 拿到扫描结果列表 | 需 `ACCESS_FINE_LOCATION`，而 `05` 已决定**不申请该权限**（未成年人产品，位置权限的合规成本远高于收益）。**没有它连扫描结果都拿不到** |

#### 4.2.2 3.0 方案：按权限档位分两条路

| 档位 | 前提 | Step 1 的做法 |
|---|---|---|
| **档 A · 三方应用身份**（默认假设） | 无 DO、无平台签名 | **不做应用内连网**。Step 1 退化为：① 显示当前是否已联网（`ConnectivityManager` 即可，无需位置权限）；② 一个「打开 WLAN 设置」按钮，跳 `Settings.Panel.ACTION_WIFI` 让用户在系统面板里连；③ 从系统面板返回时**重新判定**连接状态 |
| **档 B · Device Owner 或平台签名 priv-app** | Q34 / Q74 答案为「是」 | 可直控 WLAN 开关、扫描与连接，回到初稿设想的完整体验 |

**档位取决于 Q34 与 Q74，这两项拍板前 Step 1 无法定稿。** 但档 A 是安全的保底方案，可以先按它实现——它不需要任何特权，且在档 B 落地后是一个纯增量升级。

需要的桥能力（**两档都只需这三项，均不需要位置权限**）：

| 桥能力 | 用途 | 失败处理 |
|---|---|---|
| 查询当前连接状态（是否联网、是否计费网络） | 渲染状态、Step 2 激活前置校验 | 视为未连接，走 4.3 的跳过路径 |
| 跳转系统 WLAN 面板 | 让用户自行连网 | 提示「请在系统设置中连接网络」并允许跳过 |
| 前后台切换回调 | 从系统面板返回时重新判定 | 用户手动刷新兜底 |

> **硬性约束（原样保留）**：桥不可用时**禁止回落到 mock 假装连接成功**。假成功会让 Step 2 的激活在真实环境中莫名失败，排查成本极高。正确行为是明确告知并允许跳过（见 4.3）。
>
> 安卓评审对这条的反馈是「合理且成本低」，但附了两个前提：**能力探测必须按单项返回而非一个总布尔**；**从系统设置返回时必须重新判定**。另建议加一条 CI 规则，禁止 H5 对桥失败兜底假数据。

### 4.3 3.0 需求 · 允许跳过，但要留痕

平板的实际使用场景包含「学校批量激活时网络拥塞」「家庭 WiFi 密码不在手边」等情况。强制连网会把用户彻底堵在第二步。

| 要求 | 说明 |
|---|---|
| 提供「稍后设置」 | Step 1 允许跳过，但需二次确认并说明「未联网时无法激活设备，部分内容不可下载」 |
| 跳过后的记录 | `OnboardProfile.wifiId` 写 `null`，与「连接失败」区分开 |

## 五、Step 2 · 设备激活

### 5.1 现状基线

三个元素：Email 输入、SN 只读展示、一个 TOS 勾选框。**激活不请求任何后端接口，勾选后必然「成功」。**

| 元素 | 现状 |
|---|---|
| Email | `type="email"`，label「Please enter your E-mail address」，placeholder「Enter email address」 |
| SN | 只读 `<p>`，内容为 `SN：` + `formatOnboardSn(getExamDeviceId())` |
| TOS | **1 个**勾选框，文案含 Terms of Service / Privacy Policy / Children's Privacy Policy 三段加粗 |

校验：

```ts
emailOk    = email.trim().includes('@') && email.trim().length > 3
emailReady = emailOk && tos
```

有输入且不合法时提示「Add an @ to continue.」。Next 文案「Activate & Proceed」。

`formatOnboardSn`（L145-148）：取 `getExamDeviceId()` 的 UUID，去掉非字母数字字符，取前 10 位转大写；为空则回落字符串 `DEVICE`。

### 5.2 3.0 需求 · 字段与校验

| 字段 | 类型 | 校验 | 默认 | 错误文案 |
|---|---|---|---|---|
| `email` | 字符串 | 见下 | 空 | 见下 |
| SN | 只读 | 不可编辑、不可选中复制以外的操作 | 设备匿名 ID 短码 | — |
| `tos` | 布尔 | 必须为 `true` | `false` | 未勾选时 Next 不可点 |

**Email 校验必须收紧。** 当前 `includes('@') && length > 3` 会放过 `a@b`、`@@@@`、`x@ y` 等明显无效值。3.0 要求：

| 层级 | 规则 |
|---|---|
| 格式 | 符合 `local@domain.tld` 基本结构：`@` 恰好一个、`@` 前后均非空、域名部分含至少一个 `.` 且 `.` 不在首尾 |
| 长度 | 总长 ≤ 254；`local` 部分 ≤ 64 |
| 字符 | 不含空格与控制字符 |
| 时机 | **失焦时校验，不在每次输入时报错**。用户刚打第一个字符就看到红字是糟糕体验 |
| 错误文案 | 按原因区分：缺 `@` → 「Add an @ to continue.」；域名不完整 → 「Enter a complete domain, e.g. name@example.com」；含空格 → 「Email cannot contain spaces」 |

> **不做的事**：不做邮箱真实性验证（发验证码）。一期无账号体系，邮箱在此仅作激活登记与后续联系用途，验证流程会把向导时长从 150 秒推到几分钟以上，代价不成比例。

### 5.3 3.0 需求 · SN 展示

SN 是设备匿名 ID 的短码，不是硬件序列号。这一点必须在需求里写清，否则容易被误解为采集了硬件标识。

| 要求 | 说明 |
|---|---|
| 数据来源 | `getExamDeviceId()`（`services/hskExamService.ts:185-191`），key `clingo-hsk-device-id`。优先 `crypto.randomUUID()`，fallback `web-${Date.now()}-${random}` |
| 不采集清单 | **不采集硬件序列号、浏览器指纹或 IP**。SN 与真实设备无对应关系 |
| 一期设计事实 | 清除浏览器数据 = 新设备，SN 会变，历史最高分相互隔离。**这是一期设计不是 bug** |
| 展示格式 | 去非字母数字后取前 10 位大写；为空回落 `DEVICE` |
| 可复制 | 应允许长按复制——客服排查问题时需要用户报出 SN |

> **需求缺口 `[待确认]`**：SN 会随清除数据而变化，而它是客服唯一能定位设备的凭据。若客服流程依赖 SN 的稳定性，则当前机制不满足要求，需要与运维确认客服实际怎么用这个号。

### 5.4 3.0 需求 · TOS 与合规（关联 `07` Q35）

**当前的一个勾选框不满足合规要求。** 这不是文案问题：

| 事实 | 后果 |
|---|---|
| 目标用户 12 岁以上，主力 13–19 岁 | 相当比例用户在多个法域属于未成年人 |
| 销往东南亚 / 欧美 / 中东 | 同时受 COPPA、GDPR 第 8 条、英国 AADC、四国 PDPA、阿联酋 PDPL 约束 |
| 当前只有一个勾选框，且包含 Children's Privacy Policy | **勾选框不构成 COPPA 要求的「可验证家长同意」** |

3.0 需求：

1. **三份文档必须可独立查看**：Terms of Service、Privacy Policy、Children's Privacy Policy 各自可点开阅读，不能只是加粗文字。
2. **同意记录必须留痕**：记录同意时间、文档版本号、设备 SN。文档改版后需重新征得同意。
3. **年龄分流**：Step 3 采集的生日必须用于判断用户是否低于所在法域的门槛年龄；低于门槛时走家长同意流程，而非直接放行。具体门槛与流程 `[待确认]`，需法务给出结论。
4. **不得把 Children's Privacy Policy 混在同一个勾选框里**——如果需要家长同意，那它就不能由孩子自己勾。

### 5.5 3.0 需求 · 激活行为与异常态

激活要真正调用后端（接口 `[待确认]`，见 `07` 第 3.3 节）。状态与文案：

| 状态 | UI |
|---|---|
| 激活中 | Next 转 loading 态并禁用，其余输入禁用。超时阈值 `[待确认]`，建议 15 秒 |
| 激活成功 | 进入 step 3 |
| 网络不可用（Step 1 已跳过） | 展示离线态：「设备将在联网后自动激活」，允许继续到 step 3，并在后台重试 |
| 后端返回失败 | 按错误码分类提示；**不得只显示「激活失败」四个字** |
| SN 已被激活 | 「该设备已激活」+ 提供继续使用的出路（不能把用户堵死） |
| 邮箱已被使用 | 一期无账号体系，此情况应被允许而非报错 |
| 超时 | 「激活超时」+ 重试按钮；重试不清空已填内容 |

### GWT · Step 2

- **Given** 用户在 email 输入框输入 `a@b` 并失焦，**When** 观察校验结果，**Then** 展示「Enter a complete domain, e.g. name@example.com」，Next 不可点。
- **Given** 用户输入合法邮箱但未勾选 TOS，**When** 观察 Next 按钮，**Then** Next 处于不可点状态。
- **Given** 用户在 step 2，**When** 点击 TOS 文案中的「Privacy Policy」，**Then** 打开可阅读的隐私政策全文，且返回后已填的邮箱与勾选状态保持不变。
- **Given** 用户已在 step 1 选择跳过网络设置，**When** 进入 step 2 并点击「Activate & Proceed」，**Then** 展示「设备将在联网后自动激活」并进入 step 3，**不出现无限 loading**。

- **Given** 页面展示的 SN 为 `A1B2C3D4E5`，**When** 用户长按该文本，**Then** 可复制该字符串。
- **Given** 用户在 step 2 正在输入邮箱，**When** 输入第一个字符，**Then** 页面不立即显示任何校验错误（校验在失焦时触发）。

| 零基础 | `clingo` | `null` | `/Home` | `replace` |
| 已知等级 | `hsk` | `1` 或 `2` | `/hsk-prep-training?level=N` | `replace` |
| 不确定 | `placement` | `null` | `/hsk-prep-test` | `replace` |

**必须用 `replace` 而非 `push`**：否则用户在落地页按返回键会退回向导，而此时 `onboarded` 已为真、向导不再渲染，会出现空白或异常。

> **不要为 HSK3–6 新开路由。** 弹窗只允许选 1/2，`hskLevel` 写入 profile 后进 `/hsk-prep-training?level=N`。这是一期硬约束。

### 7.3 3.0 需求 · 「Go Back」必须保留

进度轨底部的 Go Back 在 step 4 同样存在，且需要保留。理由：学习路径是五步里**唯一影响后续长期体验**的选择，用户很可能想回去改一下昵称或语言再决定。

Go Back 在 step 4 的行为：关闭 HSK 弹窗（若开着）+ 回到 step 3，**不清除任何已填内容**。

### 7.4 3.0 需求 · HSK 等级弹窗

| 元素 | 要求 |
|---|---|
| 标题 | Select Your HSK Level |
| 说明文案 | HSK 1 and HSK 2 are open in phase one. |
| 等级网格 | `HSK_DIALOG_LEVELS = [1,2,3,4,5,6]`，六格全部渲染 |
| 开放等级 | **仅 1 与 2**（`isPhaseOneHsk`） |
| 锁定等级 | 3–6：`disabled` + `opacity: 0.4` + `LockOutlinedIcon` + `aria-label` 用 `onboard.hskLocked`（"HSK {{level}} locked"） |

| Continue 启用条件 | `hskPick === 1 \|\| hskPick === 2` |

**为什么把 3–6 渲染出来而不是隐藏**：让用户看到产品的完整等级体系（这是购买决策与续费预期的一部分），同时明确当前只开放前两级。这是刻意的产品决策，不是未完成的实现。

### 7.5 3.0 需求 · 等级锁定是硬约束

一期锁定规则在 3.0 内仍然是**硬约束**（见 `00` 第四节）：

| 层级 | 要求 |
|---|---|
| UI 层 | HSK3–6 不可点，视觉上明确为锁定态 |
| 请求层 | **不请求任何 HSK3+ 的试卷数据** |
| 路由层 | **不能通过手输 URL 绕过**。`/hsk-prep-training?level=5` 必须被拒绝并回落到允许的等级或提示锁定 |

> 详细的三层锁定实现与回归用例见 `03-HSK备考.md` 第九章（含「勿假设 URL 安全」告警）。本篇只负责向导侧的入口约束。

### 7.6 异常态

- **Given** 用户在 HSK 弹窗选中 HSK2，**When** 点击 Continue，**Then** 导航到 `/hsk-prep-training?level=2`，且 `clingo-onboard-profile-v1` 中 `path` 为 `hsk`、`hskLevel` 为 `2`。

## 八、向导拦截、跳过与重入

### 8.1 缺陷 D1 · 向导可被任意路由绕过

**现状基线**

```ts
// OnboardingContext.tsx:31,55
active = (pathname === '/Home' || pathname === '/library') && !onboarded
```

拦截范围只有两条路由。直接访问 `/hsk-test`、`/ai-chat`、`/camera`、`/apps`、`/profile` 等**任意其他 66 条路由，完全不触发向导**。一台从未激活的设备可以直达全部功能。

**为什么这是 P0 而不是小问题**：向导是激活流程与 TOS 同意的唯一入口。绕过它意味着——用户没同意任何条款就在用产品；设备没激活记录；语言、学习路径、个人资料全部为空，而下游功能（如 `05` 的 Profile、`02` 的当前教材）会拿到空值走进未定义分支。

**3.0 需求**

| 要求 | 说明 |
|---|---|
| 拦截范围 | `onboarded` 为假时，**任意路由**都渲染向导覆盖层 |
| 实现位置 | 提升到路由守卫或 `MainLayout` 层，不再由单个页面组件（`HomeEntryPage`）判断 |
| 模态性 | 向导为模态，**不可退出**：无关闭按钮、系统返回键不退出向导 |
| 深链保留 | 用户原本要去的目标路由应被记住，向导完成后跳转到该目标而非一律回 `/Home`。**例外**：Step 4 的三条路径 CTA 有自己的落地目标，优先级高于深链目标 |
| 官网 embed 例外 | `?mode=website` 的嵌入场景**不展示向导**（官网 iframe 里弹开机向导是荒谬的）。该场景走独立的最小化初始化流程 `[待确认]` |

### 8.2 缺陷 D2 · 开发后门泄漏到生产

**现状基线**

Studio 顶栏有一个「灯」按钮，`toggleStudioOnboard()`（`ShellTopBarProductLinks.tsx:158-167`、`MainLayout.tsx:310-313`），在生产 UI 里**可见且可点**：

| 当前状态 | 点击后果 |
|---|---|
| 已完成向导 | `restartOnboarding()`——**清掉 `clingo-onboard-profile-v1` 与 `clingo-onboarded-v1`** |
| 未完成向导 | `skipToHome()`——直接跳过向导 |

也就是说：一个正常使用产品的用户，误触顶栏这个不起眼的图标，就会丢掉全部个人设置并被扔回开机向导。

**3.0 需求**

| 方案 | 要求 |
|---|---|
| 首选 | **仅在 dev 构建中渲染该按钮**，生产构建中不存在于 DOM |
| 备选 | 若产品确需在生产提供「重置设备」能力，则移入 `/profile` 或系统设置的深层入口，需**长按 + 二次确认弹窗**，确认文案明确说明「将清除全部个人设置并重新开机设置」 |
| 禁止 | 保持现状——顶栏单击即清数据，无任何确认 |

### 8.3 `skipToHome()` 写入的最小 profile

**现状基线**：`skipToHome()` 写入的 profile 各字段为——`path: 'clingo'`、`email` / `nickname` / `dob` / `gender` 全为**空字符串**、`avatar: 'clingo'`、`wifiId: null`、`hskLevel: null`。

**3.0 需求**：跳过路径写入的 profile 必须能被下游安全消费。

| 要求 | 说明 |
|---|---|
| 空值语义 | 空字符串与「用户选择不填」必须可区分。建议未采集字段写 `null` 而非 `''` |
| 下游兜底 | 所有消费 profile 的位置（Profile 页、首页问候语、内容分级、HSK 默认等级）必须能处理字段缺失，见第九章 |
| 生产可达性 | 若按 8.2 首选方案，`skipToHome()` 在生产不可达，则它只是开发工具，无需产品级完备性 |

### 8.4 重入机制

**现状基线**：URL 参数 `?onboard=reset` 会清 `localStorage` 并重入向导（`OnboardingContext.tsx:22-28`）。

**3.0 需求**

| 要求 | 说明 |
|---|---|
| 保留 | `?onboard=reset` 保留作为测试与客服排查手段 |
| 不宣传 | 不在任何面向用户的界面暴露该参数 |
| 二次确认 | 该参数触发时须弹确认框说明将清除全部设置，避免通过分享链接误伤用户 |
| 与 8.2 的关系 | 这是重置能力的**唯一**生产可达路径（若 D2 按首选方案处理） |

### 8.5 异常态

| 场景 | 3.0 要求 |
|---|---|
| `clingo-onboarded-v1` 为 `'1'` 但 profile 键缺失或 JSON 损坏 | 视为**未完成向导**并重新展开。宁可让用户重走一遍，也不要让下游拿到损坏数据 |
| profile JSON 可解析但缺必填字段 | 同上 |
| 向导过程中用户切到后台再回来 | 保持当前步骤与已填内容，不重置 |
| 多标签页同时打开且其中一个完成了向导 | 另一个标签页应在下次导航时感知到 `onboarded` 变化，不再展示向导 |

### GWT · 拦截与重入

- **Given** 一台未完成向导的设备，**When** 用户直接访问 `/ai-chat`，**Then** 页面渲染向导覆盖层而非 AI 对话页。
- **Given** 一台未完成向导的设备，**When** 用户直接访问 `/hsk-test` 并完成全部五步向导（选择「零基础」路径），**Then** 落地页为 `/Home`（Step 4 的 CTA 目标优先于深链目标）。
- **Given** 向导正在展示，**When** 用户按下系统返回键，**Then** 向导不关闭，页面不退出到空白。
- **Given** 生产构建，**When** 检查 Studio 顶栏，**Then** 不存在会触发 `restartOnboarding()` 或 `skipToHome()` 的单击按钮。
- **Given** 设备 `clingo-onboarded-v1` 为 `'1'` 而 `clingo-onboard-profile-v1` 内容为非法 JSON，**When** 用户打开应用，**Then** 向导重新展开，且不抛出未捕获异常。
- **Given** 用户通过带 `?onboard=reset` 的链接打开应用，**When** 页面加载，**Then** 先弹出确认框说明将清除全部设置，用户取消则不清除任何数据。
- **Given** 官网通过 `?mode=website` 嵌入 `/hsk-prep-training`，**When** iframe 加载，**Then** 不展示开机向导覆盖层。

## 九、数据存储与字段消费

### 9.1 现状基线

`onboardingStorage.ts` 全文只有三个函数：`writeOnboarded()`、`clearOnboarded()`、`readOnboarded()`。

```ts
ONBOARD_DONE_KEY    = 'clingo-onboarded-v1'        // 值恒为 '1'
ONBOARD_PROFILE_KEY = 'clingo-onboard-profile-v1'  // 值为 OnboardProfile 的 JSON

type OnboardPath     = 'clingo' | 'hsk' | 'placement'
type OnboardHskLevel = 1 | 2 | null
type OnboardProfile  = {
  path, localeId, email, nickname, dob, gender, avatar, wifiId, hskLevel
}
```

### 9.2 缺陷 D3 · 五个字段只写不读

**没有 `readProfile()`。** 整个仓库里没有任何地方读取 `clingo-onboard-profile-v1` 的内容。后果是：

| 字段 | 采集了 | 被消费了 |
|---|---|---|
| `path` | 是 | **否** |
| `localeId` | 是 | 否（语言另有 `c-lingo-ui-locale-v1`） |
| `email` | 是 | **否** |
| `nickname` | 是 | **否** |
| `dob` | 是 | **否** |
| `gender` | 是 | **否** |
| `avatar` | 是 | **否** |
| `wifiId` | 是 | **否** |
| `hskLevel` | 是 | **否** |

**用户花 150 秒填的东西，一个字节都没用上。** 这解释了 `05` 观察到的现象——Profile 页不持久化、显示的是硬编码默认值。

### 9.3 3.0 需求 · 补 `readProfile()` 并定义全部消费方

必须提供 `readProfile(): OnboardProfile | null`，并且**每个采集的字段都要有明确的下游消费方**。没有消费方的字段应当不采集（见 6.4 的 `gender`）。

| 字段 | 3.0 消费方 | 消费方式 |
|---|---|---|
| `path` | `/Home` 与 `/AI` 的首屏推荐位 | 决定首页优先展示教材主线还是备考入口 |
| `localeId` | 与 `c-lingo-ui-locale-v1` 合并为单一来源 | 见第十二章。**两份语言状态不应并存** |
| `email` | 激活记录、客服排查 | 只在 `/profile` 展示，可编辑 |
| `nickname` | `/profile`、`/profile/edit`、**首页问候语** | 首页显示「Hi, {nickname}」；空值时回落通用文案 |
| `dob` | **年龄分流**（合规）+ 内容分级 | 见 6.3 与 `07` Q35 |
| `gender` | **建议移除**（`07` Q37） | 若保留，仅 Profile 徽章 |
| `avatar` | `/profile`、顶栏 `HubLangProfile` 头像 | 顶栏头像应显示用户所选，而非固定资源 |
| `wifiId` | 无产品消费方 | **建议不落 profile**，网络状态应实时查询系统而非存快照 |
| `hskLevel` | **HSK 备考默认等级** | `/hsk-test`、`/hsk-prep-training` 的默认等级预选 |

### 9.4 3.0 需求 · 字段缺失的兜底规则

`readProfile()` 可能返回 `null`（跳过路径、数据损坏、旧版本升级）。所有消费方必须定义兜底，**不允许出现 `undefined` 泄漏到 UI**。

| 消费场景 | 字段缺失时的兜底 |
|---|---|
| 首页问候语 | 显示通用文案（如「Welcome back」），不显示「Hi, undefined」 |
| 顶栏头像 | 显示默认头像 `clingo` |
| HSK 默认等级 | 不预选任何等级，让用户自己选 |
| 内容分级 | 按最严格档位过滤（未知年龄按未成年人处理） |
| Profile 页 | 字段显示为「未设置」+ 可点击补充 |

### 9.5 3.0 需求 · schema 版本与迁移

键名带 `-v1` 后缀，**但没有任何迁移逻辑**。一旦 `OnboardProfile` 结构变化（本篇已提议移除 `gender`、`wifiId`，新增家长同意记录），旧数据会怎样是未定义的。

| 要求 | 说明 |
|---|---|
| 版本字段 | profile JSON 内应含 `schemaVersion` 数字字段，不只靠键名后缀 |
| 迁移时机 | 应用启动时、任何读取之前，执行一次迁移 |
| 迁移方式 | 读旧结构 → 转换 → 写新结构 → 删旧键。失败则视为未完成向导（见 8.5） |
| 向前兼容 | 读到比当前代码更新的 `schemaVersion` 时，不尝试解析，视为未完成向导 |
| 统一治理 | 本节要求是 `07` 附录 E2 / E5「统一存储封装」的一部分，实现时应复用同一套 `storage` 模块，不要单独为向导写一套 |

> **完整 `localStorage` 键表见 `07-附录.md` 第二节**（26 项，含值形状、写入方、读取方）。本节只覆盖向导相关的两个键。

### GWT · 数据存储

- **Given** 用户完成向导时昵称填的是「Alex」，**When** 重启应用并进入 `/profile`，**Then** 页面展示的昵称为「Alex」而非硬编码默认值。
- **Given** 用户完成向导时选择了「已知等级 → HSK2」，**When** 之后进入 `/hsk-test`，**Then** 等级选择器默认预选 HSK2。
- **Given** 用户完成向导时选择了 `mark` 头像，**When** 观察壳层顶栏头像，**Then** 顶栏显示 `mark` 头像而非固定的 `clingo` 资源。
- **Given** `clingo-onboard-profile-v1` 中 `nickname` 为空字符串，**When** 打开 `/Home`，**Then** 问候语显示通用文案，页面上不出现「undefined」或「Hi, 」这类残缺文本。
- **Given** 存储中是旧版本 profile 结构（含已移除的 `gender` 字段、无 `schemaVersion`），**When** 应用升级后首次启动，**Then** 数据被迁移到新结构，用户不需要重走向导，且旧键被清除。
- **Given** profile JSON 的 `schemaVersion` 高于当前代码支持的版本，**When** 应用启动，**Then** 视为未完成向导并展开向导，不抛异常、不展示错乱数据。

### 10.6 缺陷 D5 · `goCamera()` 的整页跳转兜底

**现状基线**

```ts
navigate('/camera')
setTimeout(() => {
  if (location.pathname !== '/camera') window.location.assign('/camera')
}, 0)
```

`window.location.assign` 是**整页重新加载**：丢失全部 React 内存态、重跑一次应用初始化、白屏一瞬。它被用来掩盖某个 `navigate()` 不生效的路由问题。

**3.0 需求**

| 要求 | 说明 |
|---|---|
| 定位根因 | 先查清 `navigate('/camera')` 为何会失效。可能原因：`MainLayout` 的 chrome 判断触发了重渲染、路由守卫拦截、事件冒泡被阻断 |
| 移除兜底 | 根因修复后**删除 `setTimeout` + `window.location.assign`** |
| 禁止扩散 | 任何页面导航都不得使用整页跳转作为兜底。若确实存在无法用 `navigate` 到达的场景，应作为路由缺陷上报而非绕过 |
| 回归验证 | 从每一个能到达 Camera 的入口分别验证一次（底栏钮、`/Home` 工具卡、`/apps`） |

### 12.3 缺陷 D6 · 没有 RTL，只有阿语文案

**这是本篇最重的需求。** 全仓库**没有任何地方设置 `dir="rtl"` 或 `[dir=rtl]` CSS**——`main.tsx` 只设了 `document.documentElement.lang`。

当前阿语的实际状态是「**阿语文案 + LTR 布局**」。`<bdi>` 与 `dir="auto"` 只能防止单个文本节点内部的双向字符错序，**整页不镜像**：

| 元素 | 阿语下的现状 | 应该 |
|---|---|---|
| 向导进度轨 | 仍在页面**左**侧 | 右侧 |
| Go Back 箭头 | 仍朝**左** | 朝右 |
| 语言卡 / 路径卡排列 | 仍从**左**往右 | 从右往左 |
| 路径卡选中 tick | 仍在**右**下角 | 左下角 |
| 底栏 tab 顺序 | 仍从**左**往右 | 从右往左 |

一个阿语用户看到的是一个「文字是阿语但骨架是英语」的界面。这不是打磨问题，是**该语言版本不可用**。

### 12.4 3.0 需求 · RTL 工程规范

#### 12.4.1 `dir` 设置

| 要求 | 说明 |
|---|---|
| 设置位置 | `document.documentElement.dir`，与 `lang` 同处设置 |
| 时机 | locale 变更时立即设置，**在首次渲染之前**——不能先渲染 LTR 再翻转，用户会看到闪动 |
| 取值 | RTL 语言（当前只有 `ar`）设 `'rtl'`，其余设 `'ltr'`。**必须显式设 `ltr` 而非留空**，否则从阿语切回英语时不会恢复 |
| 向导覆盖层 | 向导是全屏覆盖层，同样受 `dir` 影响，不需要单独处理 |

#### 12.4.2 用逻辑属性替换物理属性

这是 RTL 落地的核心技术手段。**凡是会随书写方向改变的属性，一律用逻辑属性**：

| 禁止 | 改用 |
|---|---|
| `margin-left` / `margin-right` | `margin-inline-start` / `margin-inline-end` |
| `padding-left` / `padding-right` | `padding-inline-start` / `padding-inline-end` |
| `left` / `right` | `inset-inline-start` / `inset-inline-end` |
| `text-align: left` / `right` | `text-align: start` / `end` |
| `border-left` / `border-right` | `border-inline-start` / `border-inline-end` |
| `border-radius` 四角写死 | 逻辑角写法，或按 `[dir=rtl]` 覆盖 |

`flex-direction: row` 会自动跟随 `dir`，**不需要**改成 `row-reverse`——手动 reverse 会在 RTL 下翻两次变回 LTR，这是最常见的 RTL bug。

> **前置依赖 `07` Q77（最低 WebView 版本基线）**：`inset-inline-*` 需 Chromium **87+**，`06` 强制的 `dvh` 单位需 **108+**。**无 GMS 的设备其 WebView 由 OEM 决定，常年停在旧版**（`07` Q75）。基线未定前，逻辑属性方案的可用性是未知的——必须先拿到目标机型的 WebView 版本，并在启动时检测、低于基线给明确升级页，**不要静默破版**。

#### 12.4.3 图标镜像规则

| 镜像 | 不镜像 |
|---|---|
| 返回 / 前进箭头 | **播放 / 暂停 / 停止**（媒体控件全球一致，播放键永远朝右） |
| 列表项的 chevron | 数字与时间显示 |
| 进度条填充方向（文本类进度） | **音频 / 视频进度条**（媒体时间轴不镜像） |
| 缩进与层级指示 | 拼音、汉字（中文内容本身始终 LTR） |
| 分步流程指示器 | **田字格**（正方形，且汉字书写方向固定） |
| 侧边栏 / 抽屉的出现方向 | Logo 与品牌图形 |

#### 12.4.4 不镜像白名单（硬性）

以下内容即使在 RTL 页面中，其**内部**也必须保持 LTR：

1. **汉字与拼音**——这是中文学习产品，教学内容的方向是知识本身，不能翻。
2. **田字格**——正方形，`aspect-ratio: 1 / 1`，笔顺方向固定（见 `04` 第九章）。
3. **数字、日期、时间、分数**。
4. **音频/视频播放器时间轴与控件**。
5. **代码、URL、邮箱地址、设备 SN**。

实现上，这些内容应包在 `dir="ltr"` 容器里，或用 `<bdi>` 隔离。

| 场景 | 3.0 要求 |
|---|---|
| 阿语字体加载失败 | 用系统阿语字体兜底，不用 Naskh 书法体，不显示豆腐块 |

### GWT · 多语言与 RTL

- **Given** 用户在向导 step 0 选择「العربية」，**When** 页面完成切换，**Then** `document.documentElement.dir` 为 `rtl`、`lang` 为阿语标识，且**首次渲染即为 RTL**（不出现先 LTR 后翻转的闪动）。
- **Given** 界面语言为阿语，**When** 观察向导布局，**Then** 进度轨位于页面右侧、Go Back 箭头朝右、语言卡从右向左排列、路径卡的选中 tick 在左下角。

- **Given** 界面语言为阿语，**When** 页面中出现汉字、拼音、数字或设备 SN，**Then** 这些内容内部保持从左到右的顺序，未被翻转。
- **Given** 界面语言为阿语且页面含音频播放器，**When** 观察播放控件，**Then** 播放键仍朝右、进度条仍从左向右填充。
- **Given** 界面语言为阿语，**When** 用户切换回英语，**Then** `document.documentElement.dir` 恢复为 `ltr`，全部布局复原，无残留镜像。
- **Given** 阿语译文中某个 key 缺失，**When** 该文案渲染，**Then** 显示英文回落文案，且所在页面布局仍为 RTL。
- **Given** 3.0 语言表已合并为单一数据源，**When** 对比向导 step 0 语言卡、顶栏语言胶囊 Menu、`/system/language-packs` 三处列表，**Then** 三者语言项完全一致。

## 十三、多分辨率适配

### 13.1 现状基线 · `figmaPx` 机制

Figma 稿基准宽 **1920**。

```ts
figmaPx(n, screenSize) = max(1, round(n * figmaScale(screenSize)))
```

`figmaScale` 的映射：

| `screenSize` | scale | 来源 |
|---|---:|---|
| `960x540` | 0.5 | 显式分支 |
| `1920x1125` | 1 | 显式分支 |
| `2000x1200` | ≈1.042 | 2000/1920 |
| **其他一律** | **≈0.533** | 默认分支 1024/1920 |

`APP_SCREEN_SIZE = import.meta.env.VITE_SCREEN_SIZE || '2000x1200'`；`MainLayout` 的 fallback **也是** `'2000x1200'`。

> **两处 fallback 必须是同一套字符串**，不能一个按 2000 一个按 1024。这是 `AGENTS.md` 已记的易错点。

### 13.2 缺陷 D8 · `1920x1080` 无分支且端口冲突

| 问题 | 后果 |
|---|---|
| `figmaScale` **没有 `1920x1080` 分支** | `dev:1920-1080` 掉进默认分支按 **1024/1920 ≈ 0.533** 缩放，渲染尺寸全错——一个 1920 宽的窗口里画着 1024 宽的界面 |
| **连 `1920x1200` 分支也没有**（`06` 评审补充实测：代码只有三个显式分支） | **`1920x1200` 是 Figma 出稿基准本身**，它掉进默认分支意味着「按稿等比 1:1 渲染」这个最基本的场景都是错的。本篇初稿漏了这条 |
| `dev:1920-1080` 与 `dev:960` **抢同一个 3002 端口** | 两者无法并行启动，而 `dev:all` 的用途就是并行 |

**3.0 需求**

| 要求 | 说明 |
|---|---|
| 补分支 | `figmaScale` 增加 `1920x1080` **与 `1920x1200`** 两个分支，scale 均为 1（三者同为 1920 宽，按宽缩放故 scale 相同） |
| 重排端口 | 每个分辨率脚本占用唯一端口，`dev:all` 可全部并行 |
| 默认分支行为 | 未知 `screenSize` 落入默认分支时**应打印警告**，而不是静默按 1024 缩放。静默是这个缺陷长期没被发现的原因 |
| 脚本文档一致 | 旧 shell 脚本（`open-all-resolutions.sh`、`start-and-open-all.sh`）注释说各分辨率都用 3001，与 `package.json` 不一致。**按 `package.json` 为准**，并修正或删除这些脚本（见 `06` 缺陷 N3） |

### 13.3 3.0 需求 · 高度分配硬约束

**这是壳层布局最容易做错的一处。** 按**宽**缩放后，1920×1200 稿的总高会超过 2000×1200 与 1920×1125 的设备高度：

| 设备 | 宽 scale | 稿高 1200 缩放后 | 设备高 | 结果 |
|---|---:|---:|---:|---|
| 2000×1200 | 1.042 | 1250 | 1200 | **超出 50** |
| 1920×1125 | 1.0 | 1200 | 1125 | **超出 75** |

因此：

| 元素类型 | 处理方式 |
|---|---|
| 固定块（顶栏、底栏） | 用 `figmaPx` 按稿出数 |
| 中间互动区 | **用 flex 吃满剩余高度** |
| 禁止 | **不要**把稿上的 160+40+960+40 全加成绝对高度——加起来一定溢出 |

### 13.4 3.0 需求 · 支持矩阵

| 分辨率 | 场景 | 优先级 |
|---|---|---|
| 2000×1200 | 目标出货机型 `[待确认]` | P0 |
| 1920×1200 | Figma 出稿基准 | P0 |
| 1920×1125 | 调试基准（scale = 1） | P0 |
| 1920×1080 | 常见平板分辨率 | P0（当前有 D8 缺陷） |
| 1024×768 | 最小支持档。**注意它不是 `npm run dev` 的默认值**——`dev` 不设环境变量、回落 `2000x1200`，所以这一档**从未被日常自测覆盖**（`07` 4.3 已更正，`AGENTS.md` 亦需更正） | P1 |
| 960×540 | 极小分辨率下限 | P1 |

> **`[待确认]`**：实际出货机型的分辨率清单需硬件方确认。当前六种分辨率是从 `package.json` 的调试脚本倒推的，不代表真实机型分布。若出货机型不在此列，`figmaScale` 需要相应补分支。

### 13.5 3.0 需求 · 田字格约束（跨篇硬约束）

虽然田字格属于 `04` 的汉字书写域，但它是**多分辨率适配的硬约束**，在此重申：

| 要求 | 说明 |
|---|---|
| 必须正方形 | `aspect-ratio: 1 / 1`，宽高相等 |
| 禁止 | **禁止用 `flex: 1`** 把格子拉成竖长/横长矩形 |
| 禁止 | 禁止用固定 `300×300` 这类写死数值（虽然宽高相等，但多分辨率下会变形）——应 `width: <figmaPx 计算值>` + `aspect-ratio: 1 / 1` |
| 适用范围 | 汉字书写界面一律遵守：Hub 预览格、Module 缩略格、Practice 主格、拼字目标格 |

### 13.6 3.0 需求 · Figma → 代码 → 文档单一数据源

缺陷 D4（底栏 10 项中 6 项不符）与 D8（缺分支）都指向同一个根因：**三处数值各自维护，没有同步机制**。

| 要求 | 说明 |
|---|---|
| 唯一准绳 | Figma 最新稿 |
| 代码常量 | 集中在少数常量文件，不散落在组件内联样式里 |
| 文档 | `AGENTS.md` 与本 PRD 的数值必须与代码常量对齐；改代码常量时同步改文档 |
| 门禁 | 建立多分辨率快照测试，尺寸变化会让快照失败（见 `06` 质量门禁） |

### GWT · 多分辨率

- **Given** `VITE_SCREEN_SIZE` 为 `1920x1080`，**When** 应用启动并渲染壳层，**Then** `figmaScale` 返回 1（而非 0.533），底栏与顶栏尺寸与 1920×1125 下一致。
- **Given** `VITE_SCREEN_SIZE` 为一个未在 `figmaScale` 中声明的值，**When** 应用启动，**Then** 控制台打印警告说明该分辨率未适配，而不是静默按 1024/1920 缩放。
- **Given** 执行 `npm run dev:all`，**When** 全部分辨率脚本启动，**Then** 每个脚本占用唯一端口，无端口冲突导致的启动失败。
- **Given** 设备分辨率为 1920×1125，**When** 渲染任一含顶栏、中间互动区、底栏的页面，**Then** 页面总高不超过 1125，中间互动区通过 flex 吸收了剩余高度，页面不出现垂直溢出。
- **Given** 汉字书写页面在 960×540 与 2000×1200 两种分辨率下渲染，**When** 测量田字格的宽高比，**Then** 两种分辨率下均严格为 1:1。
- **Given** 未设置 `VITE_SCREEN_SIZE`，**When** 对比 `figmaScale` 的 fallback 与 `MainLayout` 的 fallback，**Then** 两者为同一字符串 `2000x1200`。
- **Given** 底栏尺寸常量被修改，**When** CI 执行多分辨率快照测试，**Then** 快照比对失败并报出变更的尺寸项。
